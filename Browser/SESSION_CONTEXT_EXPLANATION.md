# Объяснение работы SessionID и Ambient Context

## Проблема и решение

### Исходная проблема

Вы столкнулись с проблемой: **при вызове открытия браузера id записывается в стек, а при вызове BrowserSessionContext.Current возвращает null**.

### Причина

Проблема была в использовании `[ThreadStatic]` атрибута для хранения стека сессий. `ThreadStatic` привязывает значение к конкретному потоку, но:

1. SDK Primo может выполнять активности в разных потоках
2. При использовании async/await контекст выполнения может переключаться между потоками
3. `ThreadStatic` не передается через границы потоков

### Решение

Заменили `[ThreadStatic]` на хранение стека в `RepoDict`:

```csharp
// Было (не работало):
[ThreadStatic]
private static Stack<string> _sessionStack;

// Стало (работает):
private const string SESSION_STACK_KEY = "__BrowserSessionStack__";
private static Stack<string> GetStack()
{
    return RepoDict.Get<Stack<string>>(SESSION_STACK_KEY);
}
```

**Преимущества использования RepoDict:**
- Глобальное хранилище, доступное из любого потока
- Не зависит от ExecutionContext или ThreadStatic
- Простая и надежная реализация
- Совместимо с любой архитектурой SDK Primo

Это гарантирует, что sessionId будет доступен во всех дочерних активностях контейнера, независимо от того, в каком потоке они выполняются.

## Новая функциональность

### Присоединение к существующей сессии

Добавлено свойство `Prop_AttachToSessionId` в активность `BrowserOpen`:

**Режим 1: Создание новой сессии (по умолчанию)**
```
┌─ BrowserOpen ─────────────────┐
│ AttachToSessionId: (пусто)    │  ← Создает новую сессию
│ SessionId: mySession          │  ← Сохраняет в переменную
└───────────────────────────────┘
```

**Режим 2: Присоединение к существующей сессии**
```
┌─ BrowserOpen ─────────────────┐
│ AttachToSessionId: mySession  │  ← Присоединяется к существующей
│ SessionId: (пусто)            │  ← Опционально
└───────────────────────────────┘
```

### Смена текущей сессии

При каждом вызове `BrowserOpen` текущий ID в ambient-контексте меняется на новый:

```
┌─ BrowserOpen ─────────────────┐
│ SessionId: session1           │  ← Создает session1
│                                │
│  ┌─ ElementClick ─────────┐   │
│  │ SessionId: (пусто)     │   │  ← Использует session1
│  └────────────────────────┘   │
└────────────────────────────────┘

┌─ BrowserOpen ─────────────────┐
│ AttachToSessionId: session2   │  ← Переключается на session2
│                                │
│  ┌─ ElementClick ─────────┐   │
│  │ SessionId: (пусто)     │   │  ← Использует session2
│  └────────────────────────┘   │
└────────────────────────────────┘
```

Это позволяет работать с несколькими браузерами одновременно, переключаясь между ними через `BrowserOpen` с `AttachToSessionId`.

## Как это работает

Это происходит потому, что:

1. **BrowserOpen** вызывает `BrowserSessionContext.Push(sessionId)` в методе `SimpleAction`
2. SDK выполняет дочерние активности контейнера
3. Дочерние активности вызывают `SessionResolver.Resolve()` в своем методе `Execute`/`TimedAction`
4. `SessionResolver.Resolve()` проверяет ambient-контекст через `BrowserSessionContext.Current`

## Как это работает правильно

### Порядок выполнения:

```
1. BrowserOpen.SimpleAction()
   ├─ Создает WebDriver
   ├─ Генерирует sessionId
   ├─ Сохраняет в RepoDict
   └─ BrowserSessionContext.Push(sessionId)  ← Регистрирует в ambient-контексте

2. SDK выполняет дочерние активности

3. ElementClick.TimedAction()  (или любая другая активность)
   ├─ Читает Prop_SessionId через GetPropertyValue
   ├─ Вызывает SessionResolver.Resolve(propValue)
   │   ├─ Если propValue не пустой → возвращает его
   │   └─ Если propValue пустой → возвращает BrowserSessionContext.Current
   └─ Использует sessionId для работы с WebDriver
```

### Ключевой момент:

**SessionResolver.Resolve() вызывается ВНУТРИ метода Execute дочерней активности**, а не при инициализации активности. К этому моменту `BrowserSessionContext.Push()` уже выполнен, и ambient-контекст содержит sessionId.

## Почему ambient-контекст не очищается автоматически

SDK Primo не предоставляет хук "после выполнения дочерних активностей контейнера". Поэтому:

- **BrowserOpen** вызывает `Push()` при открытии
- **BrowserClose** вызывает `Pop()` при закрытии (в блоке finally)

Это означает, что пользователь должен **явно добавить BrowserClose** в конец контейнера или после него.

## Правильное использование

### Вариант 1: BrowserClose внутри контейнера (рекомендуется)

```
┌─ BrowserOpen ─────────────────┐
│                                │
│  ┌─ ElementClick ─────────┐   │
│  │ SessionId: (пусто)     │   │  ← Берет из ambient-контекста
│  └────────────────────────┘   │
│                                │
│  ┌─ ElementInput ─────────┐   │
│  │ SessionId: (пусто)     │   │  ← Берет из ambient-контекста
│  └────────────────────────┘   │
│                                │
│  ┌─ BrowserClose ─────────┐   │
│  │ SessionId: (пусто)     │   │  ← Берет из ambient-контекста
│  │ + вызывает Pop()       │   │  ← Очищает контекст
│  └────────────────────────┘   │
│                                │
└────────────────────────────────┘
```

### Вариант 2: BrowserClose после контейнера

```
┌─ BrowserOpen ─────────────────┐
│ SessionId: mySession          │  ← Сохраняет в переменную
│                                │
│  ┌─ ElementClick ─────────┐   │
│  │ SessionId: (пусто)     │   │  ← Берет из ambient-контекста
│  └────────────────────────┘   │
│                                │
└────────────────────────────────┘

┌─ BrowserClose ────────────────┐
│ SessionId: mySession          │  ← Использует переменную
│ + вызывает Pop()              │  ← Очищает контекст
└───────────────────────────────┘
```

## Тестирование

Тесты в `Primo.MIA.Tests/Browser/SessionIdTests.cs` проверяют:

1. **BrowserSessionContext**:
   - Push/Pop работают корректно
   - Поддержка вложенных контейнеров (стек сессий)
   - Безопасность при пустом стеке

2. **SessionResolver**:
   - Приоритет явного sessionId над ambient-контекстом
   - Fallback на ambient-контекст при пустом свойстве
   - Исключение при отсутствии обоих источников

3. **Интеграционный тест**:
   - Симуляция полного workflow с вложенными контейнерами
   - Проверка корректности разрешения sessionId на каждом уровне

## Вывод

Механизм работает правильно, если:

1. **BrowserOpen** вызывается первым и регистрирует сессию через `Push()`
2. Дочерние активности оставляют `Prop_SessionId` пустым (или заполняют явно)
3. **BrowserClose** вызывается в конце для очистки контекста через `Pop()`

Ambient-контекст позволяет избежать явной передачи sessionId через свойства всех активностей, делая workflow более чистым и удобным.
